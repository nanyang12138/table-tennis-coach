# 分析规程：从视频到结论（给 Claude 的操作步骤）

> 原则：**图片是证据，数字是辅助，技术卡是标准。**
> - 脚本负责测量：画骨架、量角度、切帧。
> - 你负责看图认动作：哪一帧是引拍结束、哪一帧在击球、拍面朝哪。你还要对照技术卡下结论。
> - 自动找出的"板"只是候选，必须核对。

下文 `<SKILL>` 表示本 skill 的目录（SKILL.md 所在目录），`$PY` 表示 setup_env.py 打印出的 `TTCOACH_PYTHON`。

## 第 0 步：问清楚（只问缺的，边跑边问）

需要知道这几件事，用户没说的才问：
- 持拍手（右手/左手）、握法（横拍/直拍）、大概水平（打了多久、有没有练过）。
- 视频里练的是什么技术，以及**来球是什么**：对方挡、推、攻过来的上旋，对拉的弧圈，搓过来的下旋，还是多球喂的什么球。选哪张技术卡取决于来球，例如拉上旋和拉下旋的要领不同。
  - 注意：技术名里的"拉""弧圈""topspin"说的是用户打出去的球，不是来球。
  - 对手或喂球的人不在画面里、用户也没说时，从画面找线索：
    - 来球从落台到被击中隔了几帧；
    - 来球弧线是高是低；
    - 节奏是否均匀、每板之间是否都完全还原（像多球或喂球）；
    - 动作像拉下旋那样"由下往上"，还是像对拉那样"向前"。
  - 还是判断不了：两张卡都对照，在报告的"前提与假设"里写明依据。随来球而变的结论只能写成条件句（"如果来球是下旋，那么……"），不能排进最需要改的 3 个问题。
- 是不是慢动作，真实帧率多少；机位在哪里。
- 画面里有几个人，分析哪一个。
- 用户自己感觉哪里不对（这往往就是要重点回答的问题）。

不要等所有答案都齐了才开始：没说的先按"右手横拍、普通视频"跑自动分析，同时提问。

## 第 1 步：环境（每台电脑只需一次）

```bash
python3 <SKILL>/scripts/setup_env.py        # 需要 Python 3.9 或更高；python3 太老时用 python3.12 等；Windows 用 py -3
```

记下最后一行 `TTCOACH_PYTHON=...`，后面都用它运行脚本。以后可以用 `--check` 确认。如果输出 `mode=frames-only`，说明这台电脑装不上骨架识别：仍然可以切帧看图，但没有角度数据，要在报告里说明。

## 第 2 步：自动分析

```bash
$PY <SKILL>/scripts/analyze_video.py <视频> --hand right [--capture-fps 240] [--start 秒 --end 秒] [--player left|right|center]
```

- 默认输出到当前目录下的 `ttcoach_<视频名>/`。
- 后续的 `--timeline`、`--at`、`--strokes` 都用同一个 `--out`，这样能复用骨架缓存。
- 每次运行都会新建自己的子目录，例如 `timeline_5.20-6.10/`、`at_1.12_1.20/`、`measured_1/`、`measured_2/`，不会覆盖之前的结果。命令输出的第一行 `out_dir:` 就是本次结果所在的目录。

## 第 3 步：先读 summary.md 的警告，判断视频能不能用

- 有 `LOW_FPS`（低于 60 帧）：拍面角度、击球瞬间、发力顺序只能粗看，报告里明确说，并建议用慢动作重拍。其他内容照常分析。
- 有 `LOW_COVERAGE`、`TRACKING_JUMPS`、`MULTI_PERSON`、`HAND_MISMATCH`：先看 timeline 图确认跟踪的人和持拍手对不对；不对就加对应参数重跑。
- 有 `POSSIBLE_SLOWMO`：问用户真实帧率，加 `--capture-fps` 重跑。
- 视频实在没法用（人太小、全程被挡）：如实告诉用户，按 recording-guide.md 给出重拍建议，不要硬分析。

## 第 4 步：看 timeline_XX.jpg，弄清整段视频

timeline 是按时间均匀抽出的画面，带骨架和 `t=` 时间标签。从这里要弄清：
- 机位是侧面、正面还是斜前方。这决定哪些数字可信，见 metrics-reference.md。
- 有几板，每板大概在什么时间，各是什么技术（正手拉、反手拨、搓……）。
- 骨架是否套在球员身上，持拍手标得对不对（橙色粗线是持拍臂）。

然后看自动候选：每个 `stroke_NN_strip.jpg`（这一板从准备前到还原后的 10 帧）和 `stroke_NN_sheet.jpg`（6 个阶段）。逐个判断：
- 这个候选是不是一板真正的击球？可能把引拍或收拍误当成一板，也可能漏掉一板。
- 它标的"CONTACT"是否真的在击球附近？

## 第 5 步：自己定出每一板的阶段时刻

对要分析的每一板（同一技术挑 3–5 板就够，优先挑画面清楚的），定出 5 个时刻（单位：秒，就是图上 `t=` 的数字）：

| 阶段 | 在画面里怎么认 |
|---|---|
| ready 准备 | 引拍开始之前、身体和拍子最"静"的一帧 |
| backswing_end 引拍结束 | 拍子**开始向前（朝球）加速之前的最后一帧**。拍子有时会先停住，再继续慢慢下沉或外移，然后才挥出；这种情况取开始向前加速之前的那一帧，而不是先停住的那一帧 |
| contact 击球 | 球压在拍面上的那一帧；看不到球时，取拍子挥得最快、经过身体侧前方的那一帧。从正面或对面拍时，来球和出球都差不多沿着视线方向，球可能连续两帧"压"在拍面上，这时只能定到 ±1 帧，报告里要说明。要看清球，用 `--at 时刻` 出 720 像素的大图 |
| finish 随挥结束 | 拍子挥到尽头、开始往回收的那一帧 |
| recovery 还原 | 拍子和身体回到准备姿势的那一帧 |

- 选准备和还原时刻时，要挑骨架已经画在人身上的帧（看 strip 或 timeline）。这两个时刻如果没有骨架，不影响这一板是否可靠，但准备和还原两个阶段的数字会是空的。
- 看不准时，对这一板出更密的画面（步长取 1/帧率，比如 240 帧视频用 0.005 秒，30 帧视频用 0.04 秒）：

```bash
$PY <SKILL>/scripts/analyze_video.py <视频> --out <同一目录> --timeline 5.2 6.1 0.02
```

## 第 6 步：按你定的时刻精确测量

```bash
$PY <SKILL>/scripts/analyze_video.py <视频> --out <同一目录> --strokes "5.28,5.44,5.60,5.72,6.00; 7.10,7.24,7.36,7.50,7.90"
```

- 这几板都是同一面时（比如全是反手），加 `--side backhand` 或 `--side forehand`，脚本就不会再按手的位置去猜正反手。
- 结果在命令输出的 `out_dir`（例如 `<目录>/measured_1/`）：
- `summary.md`、`analysis.json`：测量结果；
- `measured_NN_sheet.jpg`：6 个阶段的画面；
- `measured_NN_zoom.jpg`：击球前后的持拍手放大图，不加骨架，用来看拍面和握拍；
- `measured_NN_strip.jpg`：这一板的 10 帧连续画面。

只想量某几个瞬间（比如准备姿势），或者要看清球在不在拍面上时，用 `--at 4.80,5.60`。它会给出 720 像素的大图、手部放大图和静态角度。

## 第 7 步：看图判断（数字只做辅助）

按技术卡的"动作分解"和"视频检查要点"两节，逐个部位看：

**先看机位能看清什么：**
- 从球台对面正面拍：
  - 膝以下通常被球台挡住，站位、步法、重心、膝角都评不了，要明确写"看不清"。
  - 正面机位下"向前"是纵深方向，`swing_path`、`contact_forward_m`、`trunk_lean_deg`（前倾）都靠深度估计，不可靠。
  - 正手的引拍和前挥大部分沿视线方向运动：**画面里拍子位置不变，不等于停顿**。要说"停顿"，必须同时确认两肩宽度（转体）和拍子在画面里的大小（远近）也没有变化，否则写"看不清"。
  - 看转体要用整段准备到击球的最小肩宽比（`shoulder_width_min`，summary 里"转体与单帧稳定性"那张表），不能只比准备和击球两帧。
- 从侧面拍：膝、髋、肘的屈伸，以及挥拍方向最可信。第 5 步说的"拍子先停住、再继续下沉"那种情况，也只有侧面机位才看得出来。

然后逐项看：

1. 脚、步法和重心：站位、启动、重心有没有从一只脚移到另一只脚（`weight_shift`；脚被挡住时只看图）。
2. 膝：屈膝程度和变化（`knee_angle_deg`、`knee_min_deg`；侧面机位才可信）。
3. 髋和腰：有没有转、转多少、先后顺序。**单机位测转体不准**，以图为主，`shoulder_turn_deg`、`hip_turn_deg` 只当参考。
4. 躯干和肩：前倾程度（`trunk_lean_deg`）、两肩高低。
5. 大臂和肘：肘离身体多远（`elbow_body_gap_m`）、肘角怎么变（`elbow_angle_deg`）。
6. 前臂、手腕、握拍：主要看 zoom 图。
7. 拍面角度：只看 zoom 图和 contact_raw 图。描述成"明显前倾 / 稍前倾 / 接近垂直 / 后仰"，并说明机位带来的透视误差。
8. 击球点：在身体的哪个方位、什么高度（`contact_height_level`、`contact_forward_m`），以及在来球的上升期、高点期还是下降期（看球的轨迹，看不到球就说看不到）。
9. 挥拍路径与发力：路径方向（`swing_path.angle_deg`）、随挥收在哪里（`finish_height_level` 对比 `head_level_finish`）、发力顺序（`sequence_ms`，帧率 ≥100 才有）。
10. 还原（`recovery_dist`），以及各板之间是否稳定（`video_metrics.consistency`）。

每一条都按"观察 → 依据（卡片章节）→ 评价"写，评价分"符合 / 需改进 / 看不清"三种。

**用数字时必须遵守：**
- **先看骨架：** 引用某个阶段的数字之前，先在 sheet 图上确认骨架确实套在手臂和身体上。骨架没套上，就不引用这个数字，并说明原因。脚本判断为骨架不稳的阶段会直接给空值，并在 `quality.notes` 里注明。
- **看范围，不看单帧：** 25–30 帧的视频里，快挥时相邻两帧的角度可能差 15–20°。肘角要看 `elbow_angle_range_deg`（前后三帧）的范围，判断是变大还是变小。
- **措辞要和数字一致：** 130–145° 不能说成"几乎伸直"。几板之间不一致时，就如实写"4 板里 2 板有、2 板没有"。
- **数字的来源：** 只能用脚本输出的数，或者卡片里有出处的数。不要自己换算单位，例如把高度等级换算成厘米。
- **没看到就不下结论：** 没看到的部位（比如被球台挡住的髋）不能下"转得少"这类结论，写"看不清"。
- **击球时间：** 25–30 帧也能粗判。数一数来球从落台到被击中隔了几帧，再看击球前 2–3 帧球是在上升还是在下落：球在远离镜头、画面里却往下走，就是在下落。看不出来就说明原因。

## 第 8 步：排出最重要的 3 个问题

按对结果影响的大小排序，通常是：
1. 站位、步法和重心：影响后面所有环节；
2. 击球点和击球时间；
3. 发力顺序和挥拍路径；
4. 拍面角度、手腕等细节。

用户自己提到的问题，即使不在前三，也要回应。

每个问题都要给出：证据、为什么重要（卡片"常见错误"一节）、怎么改（具体到身体部位）、怎么练（卡片"练习方法"一节，写明组数和次数）。

## 第 9 步：和三位标杆对照

- 只用技术卡和球员档案（../players/）里**有出处**的说法。
- 三人都是右手横拍；用户是左手时左右互换来说，直拍用户参考 ../techniques/penhold.md。
- 不要说"马龙的肘角是 X 度"：公开资料里没有这三人的关节角度测量值。

## 第 10 步：写报告

按 report-template.md 写。最后给出下次怎么拍的建议，针对这次没看清的地方。

## 照片怎么分析

```bash
$PY <SKILL>/scripts/analyze_video.py <照片> --hand right
```

输出 `photo_annotated.jpg`（带骨架）、`photo_hand_zoom.jpg`（手部放大）和静态角度。
- 握拍照片：对照 ../fundamentals/grip.md；
- 准备姿势照片：对照 ../fundamentals/ready-stance.md；
- 某个击球瞬间的照片：对照相应技术卡，但要说明单张照片看不出动作过程。

## 诚实规则（必须遵守）

- **引号只能用于原文：** 发报告前，把每一处加了引号的话、每一个"卡片 §x / 第 n 条"，逐条在当前文件里 grep 一遍。找不到原文的，改成不加引号的转述，并写明出处。
- **核对引文的语境：** 被引的话讲的是哪个阶段、哪种技术，要和你要说明的现象一致；只是相近的现象，就写"类似"，不写"也是"。
- **文件可能更新过：** skill 文件的修改时间晚于你第一次读取时，重新读一遍被引用的那一节。

- 每个判断都要指得出证据：第几板、什么时刻、哪张图、哪个数字。
- 看不清就写看不清，不猜。
- 数字是单机位估计：引用时说明机位和可信度，不要和论文数值直接比大小。
- 自动候选和你核对的结果不一致时，以你看图核对的为准，并在报告里说明。
- 不做医学判断：用户提到疼痛或伤病时，建议找医生或康复师。可以参考 ../training/physical-and-injury.md 里的一般性预防建议。
